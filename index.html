Concept 1: Hosted LLM APIs vs. Self-Hosted Open-Source Models

Status: 🟢 Understand the concept

What is it?

Choosing between renting an AI brain via external managed API (e.g., OpenAI, Gemini) vs. hosting a free, public model blueprint (e.g., Llama) on our own cloud infrastructure (Azure/AWS).

Why care as a DM?

APIs offer rapid time-to-market with zero infrastructure maintenance, but carry variable Operational Expenditure (OpEx) costs and external data privacy considerations. Open-Source requires high upfront Capital Expenditure (CapEx) and deep cloud expertise, but guarantees data residency and predictable long-term costs.

Questions to Ask

  • What is our projected user volume, and where is the tipping point where self-hosting becomes cheaper than API tokens?
  • Does the client's compliance policy strictly prohibit sending data to third-party endpoints?

Risks

  • API Dependency: Vulnerability to unexpected third-party service outages or price changes.
  • Open-Source Overhead: Underestimating the ongoing maintenance costs of dedicated GPU cloud servers.

Simple Analogy

APIs = Uber: Fast, convenient, and zero maintenance, but expensive for constant heavy usage.
Open-Source = Owning commercial delivery vans: High upfront purchase cost and requires your own mechanics, but far cheaper for high-volume, predictable operations.

Concept 2: Version-Controlled Documentation (Docs-as-Code)

Status: 🟡 Know how to configure or use it

What is it?

Writing technical and delivery documentation in lightweight formats (Markdown/HTML) and managing it inside a Git repository directly alongside the codebase, using automated pipelines (GitHub Pages/Actions) to publish it live.

Why care as a DM?

It eliminates document fragmentation (e.g., lost Word docs or outdated Confluence pages), creates an immutable audit trail of delivery decisions, and ensures delivery playbooks sit right where the engineering team works.

Questions to Ask

  • Is our technical architecture documented alongside our codebase, or is it scattered across personal drives?
  • Do our CI/CD pipelines automatically validate and publish documentation updates upon code commits?

Risks

  • Deployment Pipeline Failures: Automated builds can fail due to minor formatting errors or environment deprecations, requiring quick diagnostic checks (distinguishing build blockers from minor warnings).

Simple Analogy

Traditional Docs = Storing paper blueprints in filing cabinets: Hard to search, easy to misplace, and quickly outdated.
Docs-as-Code = A digital live-syncing dashboard on the factory floor: Every time an engineer changes a machine part, the user manual updates automatically on the screen.

Concept 3: AI Agent Team Topology & Roles

Status: 🟢 Understand the concept

What is it?

The specialized staffing structure required to scale AI applications beyond traditional software development, introducing roles focused on cognitive architecture, data fuel, and non-deterministic testing.

Core Profiles

  • AI Solution Architect: Designs the systemic blueprint, enterprise landing zones, and core frameworks.
  • AI Engineer: Constructs individual agent logic, prompt rules, and tool integrations.
  • Data Engineer: Prepares, vectors, and securely routes internal enterprise data (RAG).
  • AI QA / Evaluation Engineer: Builds automated regression testing workflows to monitor agent accuracy.

Why care as a DM?

Staffing an AI project with a generic software engineering mix creates major delivery bottlenecks. You must explicitly source profiles that understand vector indexing and non-deterministic testing.

Questions to Ask

  • Do we have dedicated Data Engineers to format unstructured client data, or are we expecting AI Engineers to do data prep?
  • Who owns automated regression testing to catch hallucinations when prompts change?

Risks

  • The Generic Staffing Trap: Hiring standard web developers and expecting them to handle complex vector search or Copilot Studio ALM setup without proper domain expertise.

Simple Analogy

Building a standard software app is like constructing a modern house (carpenters, electricians, plumbers). Building an AI Agent system is like running a high-end restaurant: you need specialized chefs (AI Engineers), quality suppliers (Data Engineers), and a head food critic (Evaluation Engineer) to test dishes continuously.

Concept 4: Agent Orchestration Frameworks & Reasoning Loops

Status: 🟢 Understand the concept

What is it?

A software framework (e.g., LangGraph) that provides a standardized structure for mapping out an agent's multi-step reasoning processes, actions, evaluations, and logic loops.

The Core Components

  • Nodes (The Actions): The individual tasks the AI performs (e.g., "Fetch transaction history").
  • Edges (The Logic/Routing): The business rules connecting steps (e.g., "If amount > £10k, route to compliance").
  • State (The Memory): A shared notepad tracking context across the multi-step execution.

Why care as a DM?

Without an orchestration framework, developers write messy, custom "if/else" code. While this might work for 1 or 2 simple tasks, it creates massive technical debt and completely stalls a project trying to scale to 20+ use cases.

Questions to Ask

  • Have the Product Managers provided clear flowcharts of the business rules, or are developers guessing the routing logic?
  • Is our AI Architect proposing an open-source framework (LangGraph) or a low-code platform (Copilot Studio)?

Risks

  • Infinite Loops & Scope Creep: Unclear edge logic causes agents to re-run steps endlessly, spiking computing costs and delaying sprint deadlines.

Simple Analogy

Building 20 custom AI use cases without a framework is like building 20 custom Lego sets without instruction manuals. Using an orchestration framework provides every developer with the exact same base grid plate—the designs can be unique, but the foundation is uniform and predictable.

Concept 5: The 3-Tier Enterprise AI Architecture

Status: 🟢 Understand the concept

What is it?

A structural classification framework inside a Microsoft/Azure corporate environment that categorizes AI solutions into three tiers based on process complexity, data scale, and deployment governance.

  • Tier A (Agent Builder): Fast, built-in, low-friction bots running natively in M365 Copilot, grounded on clean text files in SharePoint.
  • Tier B (Copilot Studio): Fully managed workflow applications using Power Automate, proactive alerts, multi-step routing, and strict environment pipelines (ALM).
  • Tier C (Azure AI Foundry): High-capacity data engines leveraging Azure OpenAI, AI Search, and Document Intelligence (OCR) to ingest heavy datasets or complex layouts.

Why care as a DM?

It directly governs your staffing requirements, software licensing, and sprint velocity. Tier A requires low effort, Tier B requires Power Platform/ALM engineering capabilities, and Tier C demands data engineers and larger cloud budgets.

Questions to Ask

  • Of our pipeline use cases, how many pass the Tier C filter (requiring deep table parsing or files >300 pages) versus standard text search?
  • Have we requested the Copilot Studio development environments from tenant admins, or are we gated by platform approvals?

Risks

  • The Platform Mismatch: Forcing a complex, table-heavy use case into Tier A because it's "free," leading to hallucinated data and ruined user trust.

Simple Analogy

Tier A = Breakroom Bulletin Board: Free, immediate, great for pinning reference docs, but cannot route mail or send alerts.
Tier B = Automated Mail Room: Sorts incoming mail, tracks signatures, and automatically sends reminders.
Tier C = Industrial Cargo Shipping Hub: Operates forklifts, parses complex customs manifests, and moves massive freight.

Concept 6: Deep Dive into Tier B Automation & Tier C Data Engines

Status: 🟢 Understand the concept

What is it?

The specific underlying technical mechanics that allow an AI system to handle automatic cross-department business workflows (Tier B) and unrefined, complex data (Tier C).

  • Power Automate (Tier B): Programmatic triggers that replace manual human steps. Auto-detects dropped files, triggers the AI agent, executes logical checks, and posts output to Teams.
  • ALM Pipelines (Tier B): Application Lifecycle Management pipelines separating environments. Moves code safely from Developer Sandboxes ➔ Test/UAT ➔ Production.
  • Document Intelligence / OCR (Tier C): Optical Character Recognition engines used to parse grids, layouts, complex tables, and text structures from scanned PDFs or dense spreadsheets.
  • Azure AI Search (Tier C): High-scale vector data systems that chunk large document archives into searchable concepts, enabling instant pinpoint retrieval.

Why care as a DM?

Tier B requires planning for environment access dependencies (Dev/Test/Prod). Tier C shifts estimations from prompt tuning to data engineering setups, requiring dedicated sprint allocations.

Questions to Ask

  • Are our Tier B deployment pipelines (ALM) managed via Azure DevOps, or are developers manually exporting solutions?
  • For table-heavy use cases, are we utilizing Azure Document Intelligence to isolate grids, or passing unstructured text directly to the model?

Risks

  • Tenant Admin Bottlenecks: Delays in provisioning Azure Key Vaults, security groups, or service principals can completely block developers.
  • Ingestion Cost Shock: Processing thousands of pages through OCR engines incurs direct, consumption-based cloud costs.

Simple Analogy

Tier B (Automation & ALM) = Factory Assembly Conveyors: Replaces manual material carrying with automated sensors. ALM ensures new equipment undergoes stress testing in a replica bay (UAT) before going onto the active factory floor.
Tier C (Azure Foundry & OCR) = Mineral Extraction Mill: Raw, dense mineral ore (scanned PDFs and 300-page booklets) cannot enter processing directly; it requires a dedicated extraction mill (Document Intelligence) to refine and tag contents first.

Concept 7: The 5-Question AI Use Case Triage Matrix

Status: 🟡 Know how to configure or use it

What is it?

A decision-tree discovery tool used during intake workshops to filter and categorize proposed business use cases into Tier A, Tier B, or Tier C before sprint estimations begin.

The 5 Intake Questions

Question If YES... Architectural Tier Delivery Impact
Q1: Needs to read complex tables, scanned PDFs, or files >300 pages? YES TIER C (Azure AI Foundry) Requires Data Engineering sprints for Azure Document Intelligence / OCR.
Q2: Requires background automation or multi-person workflows? YES TIER B (Copilot Studio + Power Automate) Requires Power Automate triggers, ALM pipelines, and notification flows.
Q3: Needs strict structured outputs (e.g., direct JSON/SQL export)? YES TIER C (Azure AI Foundry) Requires strict schema-enforcement code, not basic prompts.
Q4: Purely retrieving verbatim answers from small, clean, text files? YES TIER A (M365 Agent Builder) Fast win. Built in days using standard SharePoint grounding.
Q5: Drives automated decisions without human oversight? YES REJECT / RE-DESIGN Compliance risk. Must enforce human-in-the-loop sign-off.

Why care as a DM?

It stops scope creep before it starts. It prevents engineers from over-architecting simple text queries and stops business stakeholders from expecting complex table-parsing systems overnight.

Questions to Ask

  • Have we run all 20 client use cases through this filter before committing to delivery dates?
  • Which stakeholder use cases fall into Tier A for quick wins, and which require Tier C infrastructure?

Risks

  • Over-Promising Tier A Simplicity: Allowing clients to assume complex PDF table parsing can be delivered instantly in basic M365 Copilot without Tier C tooling.

Simple Analogy

Tier A = ER Minor Scrape: Quick Band-Aid, out the door in 10 mins.
Tier B = Broken Arm: Standard casting procedure with scheduled follow-ups (Power Automate).
Tier C = Major Surgery: Specialized surgeons (Data Engineers) and heavy operating rooms (Document Intelligence/OCR).
